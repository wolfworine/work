Los 6 pilares del Spec-Driven Development

n SPEC antes de código
Define problema, flujos y contratos antes de que la
IA genere una línea.

n Decisiones versionadas
ADR registran el por qué. La IA tiene contexto, no
improvisa.

n Agentes coordinados
Modelos especializados: seguridad, dominio, UX,
generación de código.

n Métricas verificables
Tokens, costo por cambio, cobertura de tests —
trazables desde el sprint 1.

n Sin Vibe Coding
El Vibe Coding produce deuda técnica masiva y
architecture drift en semanas.

nn Supervisión senior
La IA amplifica al arquitecto. El senior valida SPEC,
ADR y decisiones críticas.

SPEC técnica detallada Arquitecto Senior
Contratos API, schemas, reglas de negocio, criterios de aceptación, seguridad y performance.

ﬁ Artefacto: SPEC.md versionado en Git · Criterio: revisado por peer + QA

04

Validación con agentes IA Orquestador IA
Agentes especializados analizan la SPEC: seguridad, dominio, UX. Cada uno entrega informe.

ﬁ Artefacto: Informe multi-agente · Criterio: 0 bloqueantes de seguridad

05

Generación de código IA + Dev
La IA genera código usando la SPEC como contexto completo. Una sola pasada limpia y testeable.

ﬁ Artefacto: PR con código + tests · Criterio: cobertura >80%, build verde

06

Review + ADR Arquitecto Senior
Valida output contra la SPEC, registra decisiones en ADR, aprueba o itera con criterio.

ﬁ Artefacto: ADR actualizado, PR aprobado · Criterio: SPEC cumplida al 100%

07

Deploy + observabilidad DevOps + Arquitecto
Deploy con feature flags, métricas de tokens y logs de decisiones IA trazables.

ﬁ Artefacto: Dashboard de métricas · Criterio: SLOs definidos en SPEC cumplidos

Ejemplo SPEC: Login seguro con MFA

CONTEXTO

El sistema usa solo password. Se requiere MFA para cumplir SOC2. Afecta 50k usuarios activos. Plazo: Sprint 14.

FLUJO

PRINCIPAL

Email ﬁ valida existencia ﬁ envía TOTP ﬁ usuario ingresa código ﬁ valida (±30s) ﬁ JWT con claim mfa:true ﬁ
dashboard.

CONTRATOS

API

POST /auth/mfa/init ﬁ {userId} ﬁ {challengeId, expiresAt} POST /auth/mfa/verify ﬁ {challengeId, code} ﬁ
{accessToken} | 401 {error: invalid_code | expired}

REGLAS

NEGOCIO

TOTP válido 5 min. Máx 3 intentos ﬁ bloqueo 15 min. Audit log obligatorio. Email en login desde nuevo dispositivo.

CRITERIOS

n Cobertura >90% en validación. n Pentesting: sin bypass MFA. n Latencia p99 <300ms. n Sin regresión en auth.

Architecture Decision Records (ADR)

Las decisiones que no están documentadas no existen para la IA.

ADR-001
Adoptar Spec-Driven Development como metodología

ACEPTADO

Contexto: Contexto: architecture drift + costos incontrolados tras Vibe Coding en sprint 8. El 45% del código requirió reescritura.

Decisión: Decisión: toda feature requiere SPEC revisada antes de generación. SPEC versionada en el mismo PR.

ADR-002
Multi-agente con modelos especializados por rol

ACEPTADO

Contexto: Contexto: un modelo general presenta sesgos según dominio. Seguridad „ generación de código „ validación UX.

Decisión: Decisión: Haiku para clasificación, Sonnet para análisis y ADR, Opus para auditorías de seguridad, GPT-4o para

generación.

ADR-003
Versionar SPECs en Git junto al código fuente

ACEPTADO

Contexto: Contexto: SPECs desactualizadas son peores que no tener SPEC. El equipo necesita que evolucionen con la

implementación.

Decisión: Decisión: /docs/specs/{feature}.md en el repo. PR de feature incluye SPEC aprobada obligatoriamente.

ADR-004
Umbral de tokens y alertas de costo por sprint

EN REVISIÓN

Contexto: Contexto: sin límites, el costo puede escalar ×100 sin control. Se evalúan tres opciones de alertas.

Decisión: Pendiente: presupuesto fijo por feature vs alerta cuando iteraciones >5 vs umbral de sprint del equipo.

Matriz de Riesgos — Sin SPEC

ALTO

Architecture Drift
La IA genera código que diverge silenciosamente de la arquitectura. Sin SPEC, nadie lo detecta hasta que el

sistema es inmantenible.

Mitiga: SPEC + review de arquitecto en cada PR

ALTO

Dead End (callejón sin salida)
Miles de líneas incomprensibles para el equipo. Sin entendimiento no se puede mantener, extender ni

debuggear.

Mitiga: SPEC limita scope. Review obligatorio.

ALTO

Vulnerabilidades críticas
El 45% del código IA sin especificación contiene vulnerabilidades. SQL injection, XSS y autenticación débil son

frecuentes.

Mitiga: Agente seguridad valida SPEC + pentesting.

MEDIO

Consumo ineficiente tokens
Sin SPEC, cada corrección reenvía todo el contexto. Iteraciones se multiplican. USD 0.20 puede costar USD 20.

Mitiga: Simulador + alertas por sprint.

MEDIO

SPEC desactualizada
Peor que no tener SPEC. Genera falsa confianza y decisiones basadas en información incorrecta.

Mitiga: PR requiere SPEC actualizada para merge.

BAJO

Overhead de documentación
La SPEC toma 1-2 días por feature. Equipos presionados intentan saltar el proceso.

Mitiga: Templates predefinidos. Se recupera en la primera iteración ahorrada.
