1. G1GC vs ZGC: Latency vs Throughput Battle
Garbage Collection strategy selection is not a theoretical decision; it dictates the entire
memory lifecycle, throughput envelope, tail-latency profile, and operational stability of a
JVM application. The choice between G1GC and ZGC determines whether a service
optimizes for throughput, ultra-low latency, cloud cost efficiency, or heap scalability. Modern
JVMs provide these two collectors as the primary choices for serious workloads.
Understanding their design philosophies is essential.
1.1 The Baseline: G1GC (Garbage First)
G1GC has been the default collector since JDK 9. It was designed to unify the strengths of
CMS (low pause) and Parallel GC (high throughput) while avoiding fragmentation and Full
GC unpredictability. G1GC uses a region-based architecture and tunable pause goals to
maintain predictable performance.
Architectural Foundations
 The heap is divided into a fixed number of uniformly sized regions (typically 1 MB
to 32 MB each; a total of 2048 regions maximum).
 Regions are not tied to “young” or “old” roles permanently; G1GC uses dynamic
region role assignment based on allocation patterns.
 Young regions are evacuated during Minor GCs. Old regions participate in concurrent
marking and selective region reclamation.
 G1GC’s design allows cleaning of both young and old objects incrementally without
pausing the entire heap.
The Garbage-First Algorithm
G1GC follows a predictive model:
1. It identifies regions containing the most garbage (highest dead-to-live object ratio).
2. It evacuates these regions first.
3. It uses a cost model to determine which regions to collect to meet the pause-time goal.
The name "Garbage First" indicates this prioritized selection process—regions with the most
garbage receive primary attention.
Latency Profile
G1GC targets predictable pause times, using the flag:
-XX:MaxGCPauseMillis=200

G1GC attempts to schedule region collections such that total work fits within the targeted
pause time. However, G1GC is not a no-pause collector. Even with aggressive tuning, worst-
case pauses on large heaps (32GB to 256GB) may degrade into:
 500 ms compaction pauses
 Multi-second worst-case Full GCs in pathological fragmentation scenarios
Strengths
 Strong throughput characteristics
 Predictable but not ultra-low pause times
 Highly tunable
 Performs well on mid-sized heaps (4 GB–64 GB)
 Lower CPU overhead than concurrent collectors
Limitations
 Pauses cannot be completely eliminated
 Humongous allocations may trigger Full GC
 Fragmentation of humongous regions produces cascading failures
 Limited suitability for sub-10ms SLA applications
1.2 The Frontier: ZGC (Z Garbage Collector)
ZGC is a fundamentally modern GC, built from the ground up for microsecond-scale pauses
and massive heap scalability. It uses colored pointers, barriers, and concurrent
relocation/remapping to ensure object movement happens while threads continue normal
operation.
Architectural Innovations
 Colored pointers embed metadata inside object references.
These colors represent mark state, relocation state, and forwarding behavior.
 Load barriers execute on every reference load.
 Concurrent relocation allows objects to move without stopping the program.
 Multi-phase concurrent cycles eliminate traditional stop-the-world phases.
ZGC works by continuously marking and relocating objects concurrently with application
threads. Only extremely small pause times occur for root scanning.
Latency Profile
ZGC guarantees:

 Sub-millisecond pause times, typically 0.1–1.0 ms
 Pauses remain constant regardless of heap size (10GB or 1TB)
This behavior is unparalleled across all GC algorithms ever used in JVM history.
Strengths
 Nearly pause-free operation
 Scales to terabyte-level heaps
 Eliminates fragmentation through concurrent compaction
 Ideal for latency-critical workloads
Limitations
 Higher CPU cost
 Higher memory overhead
 Sensitive to CPU throttling (e.g., Kubernetes CPU limits)
 Requires consistent spare compute capacity for background GC threads
ZGC prioritizes tail-latency at the expense of raw throughput.
1.3 Memory Footprint Trade-offs
Both collectors handle memory differently.
ZGC Overheads
ZGC requires:
 Extra bits in pointers (colored pointers)
 Concurrent marking threads
 Concurrent relocation threads
 Load barriers on pointer dereference
This creates:
 A 1–5% global CPU penalty
 Additional native memory overhead
 Increased code-path complexity
These costs are justified when latency predictability is a hard requirement.

G1GC Overheads
G1GC:
 Requires fewer CPU threads
 Does not intercept every reference load
 Achieves higher throughput at lower CPU cost
 May introduce pause spikes during compaction cycles
In CPU-constrained environments, G1GC is more resource-efficient.
1.4 Workload Decision Matrix
GC selection depends on workload characteristics:
Choose G1GC when:
 Applications prioritize raw throughput
 Latency jitter of 50–200ms is acceptable
 Running inside CPU-constrained containers
 Executing batch, reporting, ETL, or offline computation
 Working with 2–32GB heap sizes
 Cloud costs must remain strictly optimized
Choose ZGC when:
 Millisecond-level tail latency matters
 High-frequency trading systems require microsecond responsiveness
 Microservices demand ultra-low P99/P999 latency
 Real-time gaming backends cannot tolerate intermittent pauses
 Large heaps (16GB to 1TB+) require scalability
 Object churn is unpredictable and dynamic
 You will pay for extra CPU to achieve ultra-low latency
Latency-sensitive systems overwhelmingly choose ZGC.

2.1 Shenandoah GC Comparison
Shenandoah GC is a Red Hat–supported ultra-low latency collector designed with:
 Brooks Pointers (per-object forwarding pointer)
 Concurrent compaction
Differences:
 ZGC uses colored pointers, eliminating the extra header word overhead.
 Shenandoah uses Brooks pointers, increasing memory overhead slightly.
 ZGC performs better on large heaps (64GB+).
 Shenandoah is efficient for mid-sized heaps with high concurrency.
On Linux/x64 in 2026, ZGC is generally preferred for enterprise workloads, while
Shenandoah remains viable on:
 ARM hardware
 Musl-based distributions
 Systems with extremely small objects
2.2 ZGC Load Barriers & CPU Penalty
ZGC performs concurrent relocation. When a Java thread reads a reference:
1. It passes through a load barrier
2. Pointer color is examined
3. If color indicates relocation, the pointer is patched to the new address
4. Execution continues without pause
This ensures that:
 No object load is unsafe
 Object movement does not require global pause
But this also means:
 Every reference load incurs extra instructions
 Average CPU cost increases 1%–5% depending on workload
 Memory-intensive applications feel a larger penalty
This trade-off is inevitable for ultra-low latency GC.

2.3 Region Sizing Effects (G1GC)
G1GC region size is determined by heap:
 Minimum 1 MB
 Maximum 32 MB
 Up to 2048 regions
Humongous Objects
Any allocation ≥ 50% of region size is treated as humongous.
 Allocated directly in humongous regions
 Bypasses Young Gen
 Retained in Old Gen until explicitly freed
 Causes fragmentation
 May force a Full GC
This frequently occurs in:
 JSON/XML payloads
 Large byte[] arrays
 ORM entities with large collections
 Image or file processing
Fix
Increase region size using:
-XX:G1HeapRegionSize=16M
Larger regions reduce the likelihood of humongous allocation.

 Extra CPU threads
 Extra memory
 Frequent background cycles
 No CPU throttling
In cloud environments:
 G1GC → cheaper, more throughput

These scenarios represent real-world GC failures encountered in large-scale production

4.1 The Humongous Object Crash (G1GC)
A microservice occasionally processed large 4 MB JSON payloads. When heap region size
was 2 MB, G1GC classified these payloads as humongous and placed them directly into Old
Gen. Under high throughput, this caused:
 Old Gen fragmentation

 Aborted markings
 Forced Full GC
 Multi-second pause times
Fix: Increase region size to 16 MB, allowing these objects to remain in Young Gen and be
collected immediately.
4.2 The ZGC Allocation Stall CPU Starvation
In a Kubernetes deployment:
 G1GC was replaced with ZGC
 Latency improved from 200ms → <1ms
 Under traffic spikes, pods froze for 5 seconds
Cause:
 ZGC needed CPU to perform concurrent marking
 CPU limits constrained the pod
 When ZGC could not clean memory concurrently, heap filled
 A forced allocation stall froze the process
Fix: Increase CPU limits and cluster capacity.
4.3 ZGC Generational Memory Leak
Pre-Java-21 ZGC was single generational.
Temporary objects lived alongside long-lived objects, producing unnecessary work during
concurrent cycles.
Fix:
Enable Generational ZGC:
-XX:+ZGenerational
This massively improves the collection of temporary objects.

5.1 Generational ZGC (2026 Edition)

5.2 SATB (Snapshot-At-The-Beginning) Marking
ZGC uses a form of SATB to ensure consistent marking:

This section provides an authoritative, expanded comparison between G1GC and ZGC as
used in modern JVMs (JDK 17–23+). It targets the analytical depth expected from
staff/principal-level backend engineers responsible for high-throughput, low-latency, and
large-heap deployments across cloud-native environments.
1. What is the fundamental difference between G1GC and
ZGC?
G1GC is a generational, region-based collector optimized for predictable pause times. It
relies on incremental, partially concurrent operations with Stop-The-World (STW) pauses
during significant phases such as root scanning, evacuation, and sometimes mixed
collections. G1GC uses region selection heuristics (Garbage-First) to minimize global impact
by collecting the regions with the highest garbage percentages first.
ZGC, by contrast, is a fully concurrent, region-based, non-generational or soft-
generational collector depending on configuration in 2026 editions. Its defining feature is
colored pointers (load barriers) that allow concurrent relocation and compaction without

pausing application threads. ZGC moves almost all GC work off STW phases; only a few
micro-phases such as root checkpointing remain, typically in sub-millisecond ranges.
In essence:
 G1GC reduces pause times using incremental regional work.
 ZGC eliminates pauses using concurrent relocation and pointer coloring.
This difference reflects architectural evolution: G1GC is a predictable, pause-reducing
collector, whereas ZGC is a near-pause-free collector engineered for massive heaps and strict
latency constraints.
2. When should you choose G1GC?
G1GC remains the best choice for general-purpose JVM services that require a balance
between throughput, latency, and resource efficiency.
Recommended scenarios:
 Heap sizes up to 8–16 GB (beyond this, region pressure and mixed collection costs
rise).
 Mid-latency workloads needing predictable but not ultra-tight pauses (10–100 ms
tolerances).
 Services running mixed allocation patterns, including bursty traffic and varying
object survival rates.
 Systems prioritizing throughput over the tightest pause bounds, such as web
backends, financial APIs, batch-oriented microservices, or high message throughput
platforms.
 Workloads with moderate long-lived object ratios, for which generational
architecture provides benefits.
G1GC remains a default, general-purpose GC with excellent performance stability,
predictable ergonomics, and mature tooling support.
3. When should you choose ZGC?
ZGC is designed specifically for ultra-low latency and large-heap (16 GB–multi-terabyte)
environments.
It is suitable when:
 Pause times must remain consistently under 2–10 ms, regardless of heap size.
 Heap exceeds 16 GB, especially 32–512 GB memory footprints.

event-driven gateways).
 CPU availability is high (ZGC benefits from substantial concurrent CPU resources).
 Memory fragmentation risk must be minimized without long pauses.
 Predictable tail latency (p99/p999) is a strict requirement.
ZGC is built for environments where GC pauses, even in the tens of milliseconds, are

4. What are G1GC regions and how do they work?
G1GC divides the heap into ~2048 uniformly sized regions (1–32 MB each depending on
heap size). These regions are categorized as:
 Eden regions (new object allocation)
 Survivor regions (live objects surviving young collections)
 Old regions (long-lived objects)
 Humongous regions (large objects exceeding half the region size)
G1GC operates by:
 Selecting “garbage-first” regions with the highest reclaimable ratio.
 Performing incremental marking of the object graph.
 Executing evacuation of selected regions during STW pauses.
 Updating remembered sets to maintain cross-region reference correctness.
This region-based structure makes G1GC more flexible and less prone to long pauses than
older collectors like CMS or Parallel GC, though it still relies on STW phases for evacuation.

1. Colored Pointers
Each pointer encodes metadata bits (mark state, remap state), enabling the GC to track
object lifecycle without stopping threads.
2. Load Barriers
Every read from a heap object triggers a load barrier that ensures the pointer is up to
date and redirects to new locations when objects have been relocated.
3. Fully Concurrent Marking and Compaction
ZGC performs:
o concurrent marking

o concurrent remapping
