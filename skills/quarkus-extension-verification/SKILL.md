# Verifying Third-Party Quarkus Extensions & Externalizing Secrets

Operational lessons from integrating `quarkus-amazon-secretsmanager` (Quarkiverse) into a
Quarkus 3 project. Framework-agnostic in spirit — the version-alignment and secrets-as-config
patterns apply to any Quarkus extension ecosystem (AWS, Azure, Vault) and, more loosely, to any
plugin-based framework where a community extension pins to a specific core-framework version.

## 1. Don't trust the first search result for a dependency version

A package-search tool (e.g. Maven Central's `solrsearch` API) can return a **stale, incomplete**
result set — in one real case it reported `3.3.1` as the latest version of a Quarkiverse
extension when `3.21.2` was actually current (18 releases newer). Search-index lag is real and
silent: no error, just wrong data presented confidently.

**Always cross-check against an authoritative source before pinning a version:**

```bash
# Maven Central's own metadata file is authoritative (no search-index lag)
curl -s "https://repo1.maven.org/maven2/<group-path>/<artifact>/maven-metadata.xml" \
  | grep -A2 "<release>"

# For an OSS extension, the GitHub Releases API is equally authoritative and gives you dates
curl -s "https://api.github.com/repos/<org>/<repo>/releases?per_page=5"
```

If the two disagree, trust `maven-metadata.xml`'s `<release>` tag — it's generated by the
repository itself at publish time, not a secondary index.

## 2. Quarkiverse/third-party extensions pin to a specific Quarkus core version — check it

A community Quarkus extension's own root `pom.xml` declares a `quarkus.version` property (or
equivalent) that its `-deployment` module was built and tested against. **Your project's
`quarkus.platform.version` (the `quarkus-bom` import) must be compatible with that** — usually
"close enough" (same major, nearby minor) rather than byte-identical, but a large gap breaks.

```bash
# Find what Quarkus core version an extension release actually targets
curl -s "https://raw.githubusercontent.com/<org>/<repo>/<tag>/pom.xml" | grep -B2 -A2 "quarkus.version"
```

**The failure mode is a trap** — it does *not* show up as a Maven dependency-resolution error
(everything downloads fine). It shows up at Quarkus augmentation/test-boot time as:

```
java.lang.NoClassDefFoundError: io/quarkus/deployment/builditem/Startable
Caused by: java.lang.ClassNotFoundException: io.quarkus.deployment.builditem.Startable
	at io.quarkus.deployment.util.ServiceUtil.classesNamedIn(...)
	at io.quarkus.deployment.ExtensionLoader.loadStepsFrom(...)
```

This looks like a missing dependency or a broken classpath, and it's tempting to debug it as
such. It's actually a **version skew between your `quarkus.platform.version` and the extension's
`-deployment` artifact**. Fix: bump your `quarkus.platform.version` to something at or above what
the extension's own pom targets, using the latest **stable, non-RC/CR** release
(`maven-metadata.xml`'s `<release>` tag again — skip `.CR1`/`.Beta` suffixes for a real project).

## 3. Externalize secrets via a ConfigSource, don't bundle them as resources

A private signing key (JWT, TLS, etc.) sitting as a plaintext `.pem` file under
`src/main/resources/` is a real, easy-to-miss security smell — it ships inside the built JAR and
into version control by default. The fix that generalizes across cloud providers: a Quarkus
**ConfigSource extension** that resolves a named secret from a real secret store into a config
property at runtime, so application code never sees a file path — only a config key that happens
to be secret-backed.

**Generalized shape** (concrete example: AWS Secrets Manager via `quarkus-amazon-secretsmanager`,
but SSM Parameter Store, HashiCorp Vault, and Azure Key Vault extensions follow the same shape):

```properties
# 1. Turn the config source on
quarkus.secretsmanager.config.enabled=true

# 2. Map an existing config property name directly to a secret name.
#    The property on the left can be ANY property another extension already reads —
#    here it's SmallRye JWT's own signing-key property, so the JWT extension never
#    knows the value came from a secret store instead of a file.
quarkus.secretsmanager.config.secrets."smallrye.jwt.sign.key"=my-app/jwt-signing-key

# 3. Point at the actual secret store (LocalStack for dev, real AWS in prod)
quarkus.secretsmanager.endpoint-override=http://localhost:4566
quarkus.secretsmanager.aws.region=us-east-1
quarkus.secretsmanager.aws.credentials.type=static
quarkus.secretsmanager.aws.credentials.static-provider.access-key-id=test
quarkus.secretsmanager.aws.credentials.static-provider.secret-access-key=test
```

Confirm it actually worked from the startup log (don't just assume the properties applied):

```
INFO  [...SecretsManagerConfigSource] Loading config values from AWS Secrets Manager...
INFO  [...SecretsManagerConfigSource] ConfigSource loaded 1 config entries from AWS Secrets Manager.
INFO  [io.quarkus] Installed features: [..., aws-secrets-manager-config-source, ...]
```

**Key insight**: the consuming property (`smallrye.jwt.sign.key` here) accepts inline PEM/secret
content specifically *because* its own docs say so ("only use this property when fetching from a
remote secret manager") — a `*.location` variant of the same property (`smallrye.jwt.sign.key
.location`) expects a file path/classpath resource instead and won't accept a config-sourced
value the same way. Check whether the property you're feeding a secret into has an inline-value
variant before assuming you need one.

## 4. LocalStack: persistent container vs. Dev Services — pick deliberately

Quarkus Dev Services can auto-provision a LocalStack container with zero config
(`quarkus.<extension>.devservices.enabled=true`, on by default for most Amazon-service
extensions). This is genuinely convenient, but it's **ephemeral** — a fresh, empty container every
time the app starts. If you need a secret/data seeded once and reused across restarts (the normal
case for a signing key that shouldn't rotate every dev-mode reload), a **persistent named
container** you start once and seed manually is the better fit — the same pattern you'd already
use for a local Postgres:

```bash
docker run -d --name my-app-localstack -p 4566:4566 -e SERVICES=secretsmanager localstack/localstack:<tag>
docker exec my-app-localstack awslocal secretsmanager create-secret \
  --name my-app/jwt-signing-key --secret-string "file:///tmp/privateKey.pem"
```

Setting an explicit `quarkus.<extension>.endpoint-override` (as in the config example above)
suppresses Dev Services automatically, the same way setting `quarkus.datasource.jdbc.url`
suppresses the Postgres Dev Services container — you don't need to explicitly disable both.

## 5. Config property renames are silent — don't ignore startup warnings

Upgrading `quarkus.platform.version` (which you may be forced into by step 2) can silently
no-op properties that were renamed between versions. Quarkus logs this, but only as a `WARN`,
easy to scroll past:

```
WARN  Unrecognized configuration key "quarkus.http.cors" was provided; it will be ignored
WARN  The "quarkus.hibernate-orm.database.generation" config property is deprecated
```

Treat every `WARN`/deprecation line in a clean-build log as something to fix immediately, not
background noise — an "unrecognized" key means the setting you think is active (CORS, schema
generation mode, etc.) is silently doing nothing. Verify the current property name from the
extension's own guide page (fetch it, don't guess/recall — property names churn across Quarkus
minor versions) and re-run to confirm the warning is gone, not just that the app still boots.

## Checklist before adding any third-party Quarkus extension

- [ ] Checked `maven-metadata.xml`'s `<release>` tag (or GitHub Releases API), not just a search tool, for the current version.
- [ ] Checked the extension's own root `pom.xml` for the `quarkus.version` it targets, and confirmed your `quarkus.platform.version` is compatible (same major, nearby minor, no huge gap).
- [ ] If a secret is involved (key, password, token), wired it through a ConfigSource extension instead of bundling a file — and confirmed from the startup log that the config source actually loaded entries, not just that the app booted.
- [ ] Decided deliberately between Dev Services (ephemeral, zero-config) and a persistent named container (manual, but survives restarts) for any local cloud emulator involved.
- [ ] Re-ran a clean build after wiring and read every `WARN` line — zero unrecognized/deprecated config keys before calling it done.
